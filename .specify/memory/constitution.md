# Conflict & War — C&W Constitution

## Core Principles

### I. Spec Kit как единый SDD-процесс

Изменения поведения MUST проходить штатный процесс GitHub Spec Kit:
спецификация → уточнения при необходимости → план → задачи → анализ →
реализация → проверка converge. Используются официальные шаблоны
`.specify/templates/` и навыки `.agents/skills/speckit-*/`.
Параллельные собственные SDD-шаблоны MUST NOT вводиться.
Спецификации функций хранятся в `specs/`; задачи закрываются только по факту.
Это сохраняет общий процесс для человека и агента.

### II. Сохранение технологического стека

Проект MUST сохранять C++20/C11, Rust workspace, CMake/Ninja, Clang, vcpkg,
SDL3, OpenGL 3.3, OpenAL Soft, ImGui, Catch2 и Trident.
Смена движка, языка, графического API или системы сборки из предпочтений запрещена.
При техническом тупике MUST быть воспроизводимый блокер, проверенные варианты
существующего стека, последствия и миграционный план в ADR.
Замена технологии требует решения владельца проекта.

### III. Явный отказ от антипаттернов

Новые антипаттерны MUST NOT добавляться. При попытке предложить или применить
их разработчик/агент MUST явно сообщить **АНТИПАТТЕРН: название**, указать
конкретный вред и предложить исправление до реализации.
Запрещены скрытие ошибок, обход проверок ради зелёного CI, скрытые зависимости
и глобальное изменяемое состояние, дублирование бизнес-логики,
жёстко заданные пути машины разработчика, преждевременные абстракции
и несвязанные с задачей массовые рефакторинги.
Унаследованные проблемы фиксируются отдельно с путём и влиянием;
они не разрешают добавлять новые случаи. Подробности: `docs/engineering.md`.

### IV. Проверяемая поддержка платформ

Обязательные целевые платформы MUST включать Windows x64 и macOS arm64.
По решению владельца от 2026-10-31 проверка macOS Intel (x86_64) исключена
из обязательной приёмки и CI: доступного хоста для её проверки нет.
Существующие Intel presets сохраняются для необязательного использования;
их наличие MUST NOT считаться доказательством работоспособности Intel.
Платформенные изменения MUST иметь воспроизводимые команды configure/build/test.
Готовность каждой платформы подтверждается её нативной сборкой и тестами;
проверка JSON или наличие CI-файла не заменяют компиляцию.
Невыполненные проверки MUST явно оставаться открытыми с указанием причины.
Игровой запуск, runtime-зависимости, упаковка и подпись проверяются отдельно.

### V. Глубокая модификация Arma и совместимость

Название MUST быть **Conflict & War**, сокращение **C&W**;
машинное имя CMake — `ConflictAndWar`.
Внутренние цели `Poseidon*`, пути `apps/cwr`, параметры `CWR_*` и `OFPR_*`
MUST сохраняться, пока отдельная спецификация не определит миграцию.
Форк MUST быть обозначен как модифицированный; LICENSE, CREDITS.md,
THIRD_PARTY_NOTICES.md и авторские уведомления сохраняются.
Сторонние игровые данные MUST NOT добавляться в исходники и CI.

## Project Constraints

На текущем этапе C&W разрабатывается как глубокая модификация
Arma: Cold War Assault Remastered по указанию владельца от 2026-10-27.
Разрешённые игровые данные используются из отдельной локальной установки;
они не копируются в исходный репозиторий и не публикуются конвейером.
Рабочее обозначение модификации не расширяет права на ресурсы или товарные знаки;
условия LICENSE и лицензий игровых данных продолжают действовать.

Baseline vcpkg и Cargo.lock сохраняются; Rust CI использует `--locked`.
Изменение процесса разработки не меняет стек приложения.
Python >= 3.11 нужен для CLI и переносимых скриптов Spec Kit.
Подготовка сборки не включает полный ребрендинг интерфейса и binaries,
игровые функции, установщики, подпись или notarization.

## Development Workflow

Спецификация содержит пользовательские сценарии, функциональные требования
и измеримые критерии успеха. План MUST пройти Constitution Check до реализации.
Задачи MUST ссылаться на конкретные файлы и пользовательские истории;
изменения и проверки связываются с требованиями.
Converge выявляет оставшиеся пробелы; цикл реализации повторяется до закрытия
критериев. Недоступные нативные проверки не отмечаются выполненными.
Документы текущей функции поддерживаются как живой контракт: при новых фактах
согласованно обновляются spec, plan и tasks. Результаты проверок можно хранить
рядом как дополнительные доказательства, без отдельного собственного процесса.

## Governance

Конституция является источником обязательных правил проекта;
AGENTS.md, CONTRIBUTING.md, планы и ревью MUST соответствовать ей.
Поправки вносятся через `$speckit-constitution` с описанием причины и влияния.
Они не отменяют указаний владельца; изменение стека требует его решения.
Версии: MAJOR — несовместимое изменение принципов; MINOR — добавление
или существенное расширение правил; PATCH — уточнение без смены смысла.
Ревью MUST проверять соблюдение конституции, отсутствие новых антипаттернов
и наличие доказательств для закрытых задач.
