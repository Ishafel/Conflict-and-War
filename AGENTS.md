# Conflict & War — C&W

## Обязательные правила разработки

- Этот репозиторий — основа **Conflict & War**, сокращённо **C&W**. На текущем этапе проект ведётся как глубокая модификация Arma: Cold War Assault Remastered, по указанию владельца от 2026-10-27. Машинное имя CMake: `ConflictAndWar`. Существующие имена `Poseidon*`, пути `apps/cwr`, параметры `CWR_*` и `OFPR_*` сохраняются для совместимости, пока отдельная спецификация не потребует миграции. Не переименовывать их массово.
- Использовать **GitHub Spec Kit** для SDD; соблюдать [конституцию](.specify/memory/constitution.md). Штатные шаблоны `.specify/templates/` и навыки `.agents/skills/speckit-*/` являются основой процесса; не создавать параллельную собственную SDD-структуру. Порядок команд — в [короткой памятке](docs/sdd/README.md). До изменения поведения подготовить спецификацию, план и задачи средствами Spec Kit.
- Сохранять текущий стек: C++20/C11, Rust, CMake/Ninja, Clang, vcpkg, SDL3, OpenGL 3.3, OpenAL, ImGui, Catch2 и Trident. Не заменять движок, язык, графический API или систему сборки из предпочтений. При доказанном техническом тупике сначала зафиксировать воспроизведение, рассмотренные варианты и последствия в ADR; смена стека требует решения владельца проекта.
- Обязательные целевые платформы: Windows x64 и macOS Apple Silicon (arm64). По решению владельца от 2026-10-31 проверка macOS Intel (x86_64) исключена из обязательной приёмки и CI из-за отсутствия доступного хоста; существующие Intel presets сохраняются как необязательные. Не объявлять платформу рабочей без результатов нативной сборки; сборка, тесты и запуск игры — разные проверки.
- **Новые антипаттерны запрещены. При попытке их предложить или добавить явно писать `АНТИПАТТЕРН: <название>`**, объяснять конкретный вред и предлагать исправление до реализации. Не обходить это правило молча.
- Запрет распространяется на обход проверок ради зелёной сборки, подавление ошибок без обработки, скрытые зависимости/глобальное изменяемое состояние, копирование бизнес-логики, несвязанные рефакторинги, жёстко заданные пути к компьютеру разработчика, преждевременные абстракции и изменение стека без доказанной необходимости. См. [политику](docs/engineering.md).
- Унаследованный код не является разрешением повторять его проблемы. Новые случаи не добавлять; найденные старые отмечать с путём, влиянием и отдельной задачей. Не переписывать весь legacy в рамках подготовки сборки.
- Каждое изменение связывать с ID требования и проверкой. Запускать подходящие проверки и честно отмечать, что не запускалось и почему. Не подменять компиляцию анализом конфигурационных файлов.
- Сохранять LICENSE, CREDITS.md, THIRD_PARTY_NOTICES.md и авторские уведомления. Новый проект обозначать как модифицированный форк; сторонние игровые данные не включать в исходники и CI.
