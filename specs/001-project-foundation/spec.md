# Feature Specification: Основа Conflict & War

**Feature Branch**: ветка не создавалась; каталог функции `001-project-foundation`.

**Created**: 2026-10-27

**Status**: Implemented — Windows x64 и macOS arm64 build/test подтверждены.

**Input**: Подготовить Conflict & War — C&W к SDD через GitHub Spec Kit,
сохранить стек, явно запрещать антипаттерны и подготовить сборку Windows/macOS.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Разработка по GitHub Spec Kit (Priority: P1)

Разработчик описывает изменение в чате и получает спецификацию, план и задачи
через стандартные навыки Spec Kit с учётом правил C&W.

**Why this priority**: Единые инструменты и правила нужны до следующей разработки.

**Independent Test**: Проверить штатную интеграцию, конституцию и выбор текущей
функции; открыть README и пройти короткую памятку.

**Acceptance Scenarios**:

1. **Given** инициализированный проект, **When** проверяется интеграция,
   **Then** официальный Spec Kit сообщает `status: ok` без отсутствующих
   или изменённых управляемых файлов.
2. **Given** новая задача, **When** агент планирует реализацию,
   **Then** применяются конституция и штатные шаблоны, без собственных SDD-шаблонов.
3. **Given** предложение сменить стек или добавить антипаттерн,
   **When** оно рассматривается, **Then** стек сохраняется до доказанного тупика
   и решения владельца, а антипаттерн явно обозначается до реализации.

### User Story 2 - Нативная сборка Windows и macOS (Priority: P1)

Разработчик выбирает preset своей платформы и получает воспроизводимые
configure/build/test-команды без замены движка и технологий.

**Why this priority**: Сборка является основой дальнейшей разработки игры.

**Independent Test**: Выполнить команды из docs/building.md на Windows x64,
macOS arm64; проверить результаты нативных CI jobs. С 2026-10-31 по решению
владельца проверка Intel исключена из приёмки из-за отсутствия доступного хоста.

**Acceptance Scenarios**:

1. **Given** необходимые инструменты и SDK, **When** выполнены команды сборки,
   **Then** C++ и Rust компилируются, Foundation CTest и Rust tests проходят.
2. **Given** отсутствующий инструмент или ошибка вспомогательной команды,
   **When** выполняется проверка, **Then** возвращается ошибка, а не ложный успех.
3. **Given** только проверенный JSON/YAML, **When** формируется отчёт,
   **Then** нативная компиляция и запуск игры остаются явно непроверенными.

### Edge Cases

- Пути проекта и исходников содержат пробелы: передавать их отдельными аргументами.
- Машина другой ОС: не предлагать основной preset как нативный для неё.
- Нет Python на PATH: установить Python >= 3.11; не вставлять путь чужой машины.
- Нет игровых данных: не выдавать базовые тесты за проверку игрового запуска.
- Не выбран каталог функции: указать SPECIFY_FEATURE_DIRECTORY штатному Spec Kit.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Название проекта MUST быть Conflict & War, сокращение C&W.
- **FR-002**: Текущий стек MUST сохраняться; смена требует доказанного тупика,
  ADR и решения владельца.
- **FR-003**: Процесс MUST использовать официальный GitHub Spec Kit,
  его конституцию, шаблоны и навыки агента; собственные SDD-шаблоны удаляются.
- **FR-004**: Новые антипаттерны MUST быть запрещены; попытка явно маркируется
  `АНТИПАТТЕРН: название` с вредом и исправлением.
- **FR-005**: Windows x64 и macOS arm64 MUST иметь единый путь configure/build/test.
  Intel presets сохраняются как необязательные; проверка Intel не входит в приёмку.
- **FR-006**: CI MUST проверять обе ОС; компиляция MUST отличаться от игрового запуска.
- **FR-007**: README MUST содержать короткую памятку для человека с командами Spec Kit.
- **FR-008**: По решению владельца от 2026-10-31 CI MUST проверять Windows x64
  и macOS arm64 без Intel job. Удаление обязательной Intel-проверки не является
  подтверждением поддержки Intel и не изменяет тесты оставшихся платформ.

### Key Entities

- **Конституция**: обязательные принципы проекта, версия и даты принятия.
- **Функция**: каталог specs с требованиями, планом, задачами и доказательствами.
- **Локальное состояние Spec Kit**: относительный путь текущей функции;
  не является общим состоянием команды и не публикуется в Git.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001** (FR-001–FR-004, FR-007): правила согласованы; штатная интеграция
  не имеет отсутствующих/изменённых файлов; README даёт порядок команд;
  каталог собственных шаблонов не содержит файлов.
- **SC-002** (FR-005): все 3 Windows и 6 macOS configure presets имеют build/test
  пары; проверки форматирования/анализа обрабатывают пробелы и возвращают ошибки.
- **SC-003** (FR-005–FR-006): каждая из двух обязательных платформ имеет успешную
  нативную сборку C++/Rust и базовые тесты. До фактического прогона критерий открыт.
- **SC-004** (FR-005, FR-007): разработчик находит требования к инструментам,
  команды, выходные каталоги и границы проверки в документации проекта.
- **SC-005** (FR-008): CI-матрица содержит только Windows x64 и macOS arm64;
  Intel presets сохранены, обязательные тестовые шаги оставшихся jobs сохранены,
  конституция, документация и активные задачи согласованы с этим объёмом.

## Assumptions

- SDD означает Spec-Driven Development; выбранный инструмент — GitHub Spec Kit.
- Полный ребрендинг runtime, новые игровые функции, установщики, подпись
  и notarization не входят в подготовку.
- Внутренние имена Poseidon*, CWR_*/OFPR_* сохраняются ради совместимости.
- Игровые данные предоставляются отдельно; нативная компиляция требует SDK
  и инструментов на каждой ОС.
